# Presentation registry and live coverage — 2026-10-10

Status: audit in progress; automated registry coverage passes, live Ollama coverage is partial.

## What the counts mean

The repository has three related counts that should not be conflated:

- **88 adaptive presentation starter packs** in `vak-presentation::seeds::built_in_seed_pack`. They are content-only layouts, automatically registered and activated by the server unless the owner suppresses them. They are not 88 separate model tools.
- **12 `emit_*_card` tool schemas** in `vak-core/src/presentation_tools.rs`. Each schema handles a payload shape and exposes one or more semantic types.
- **109 unique built-in semantic types** accepted by the delivery registry. These are the names a model may select through an emitter's `semantic_type` field.

The normal turn path remains request/context planning → admitted and discoverable tools → validated emitter call → presentation ledger entry → server projection → client renderer. Adaptive packs are an optional layout layer over that path. They do not replace tool discovery, the session ledger, or the renderer registry.

## Automated coverage

The following checks pass on this tree:

- `vak-core::presentation_tools::tests::every_registered_semantic_type_across_all_shapes_renders` exercises every registered type through its owning tool schema and presentation builder.
- `vak-core::presentation_tools::tests::search_finds_the_right_emitter_for_every_registered_semantic_type` checks that discovery ranks the owning emitter first for every registered type.
- `vak-server::projection::tests::every_supported_type_renders_through_the_full_path_at_any_size` checks every type through the full projection path at small and large payload sizes.
- `vak-core::presentation_tools::tests::every_starter_presentation_pack_compiles_with_its_emitter_payload` (added in this audit) compiles each accepted semantic type for all 88 starter packs with schema-valid payloads from the corresponding emitter fixtures.
- `vak-agent` unit tests cover the bounded completeness check, including that unchanged output cannot consume retries and that no capacity for an internal check does not turn an otherwise completed response into a failed run.

These checks establish registration, tool discoverability, schema acceptance, and renderer/projection coverage. They do not establish that a live model chooses the right card for every possible request.
