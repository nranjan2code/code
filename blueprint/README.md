## What it is

Vakyartha (`vak`) is a local-first agent harness for one owner: agents that work on code, documents, research and everyday tasks, reached from a desktop app, the browser, a terminal and chat apps, with every model input and tool result kept in an append-only record. Its thesis is strong safety, transparent operation, extensible integrations and a simple core.

The lower layers (storage, permission, the pure deciders, the document engines) are well shaped and change rarely. Above them, three large crates (`vak-core`, `vak-agent`, `vak-server`) hold the turn and most features, and that is where most of the work and most of the risk sit.

## How it connects

838 connections between subsystems, measured from the code: a module naming another (a Rust path or item, a method defined once, a TypeScript import) or a client naming a route ([harness/connections.py](harness/connections.py)). The flows below are written by hand, and each step must ride a measured connection or the harness reports it. [blueprint.html](blueprint.html) draws them as an animated plant diagram.

**A message becomes an answer**

1. owner → Workspace client: type a message
2. Workspace client → HTTP service: POST the message
3. HTTP service → Turn admission: run the turn
4. Turn admission → Intent kernel: read the request
5. Turn admission → Capability registry: bind the tool surface
6. Turn admission → Runs, effects and cursors: open the run
7. Turn admission → Agent loop: start the loop
8. Agent loop → Context engine: plan the working set
9. Agent loop → Model providers and routing: stream the model
10. Model providers and routing → models: call the provider
11. Agent loop → Permissions and provenance: authorize each call
12. Agent loop → Built-in tools and the worker: run the calls
13. Built-in tools and the worker → Sandbox and execution: in a sandboxed worker
14. Agent loop → Ledgers and records: record results
15. Agent loop → Control plane and judges: check the plan
16. Agent loop → Cards and presentation: record cards
17. Cards and presentation → HTTP service: project what a person sees
18. HTTP service → Workspace client: stream events
19. Workspace client → owner: the answer, card by card

**A chat message from a phone**

1. chat → Gateway and channels: a message arrives
2. Gateway and channels → Permissions and provenance: check the allowlist
3. Gateway and channels → Turn admission: admit as the bound Agent
4. Turn admission → Agent loop: run the loop
5. Agent loop → Cards and presentation: record cards
6. Cards and presentation → Delivery: render for the channel
7. Delivery → Gateway and channels: channel markup
8. Gateway and channels → Runs, effects and cursors: send once as an effect
9. Gateway and channels → chat: the reply

**A scheduled automation runs**

1. Automations and triggers → Runs, effects and cursors: claim the slot
2. Automations and triggers → Turn admission: run the turn
3. Turn admission → Agent loop: run the loop
4. Agent loop → Ledgers and records: record the work
5. Automations and triggers → Inbox and digest: report how it ended

**An Office edit goes through Review**

1. Agent loop → Built-in tools and the worker: call office_apply
2. Built-in tools and the worker → Office and PDF documents: edit in the worker
3. Office and PDF documents → Sandbox and execution: write a draft
4. Office and PDF documents → Library and file state: record a version
5. Workspace client → Library and file state: the owner reviews
6. Library and file state → Sandbox and execution: promote, with undo

**Mail is sent after review**

1. Workspace client → Mail and calendar: approve the candidate
2. Mail and calendar → Runs, effects and cursors: send once as an effect
3. Mail and calendar → mailproviders: the provider sends it

**A worker is delegated**

1. Agent loop → Workers and delegation: call task
2. Workers and delegation → Turn admission: run a child turn
3. Workers and delegation → Ledgers and records: keep the child's ledger

**An older turn is recalled**

1. Agent loop → Recall and history: call recall
2. Recall and history → Catalog and search: search the catalog
3. Catalog and search → Ledgers and records: open the turn

**A source is read**

1. Automations and triggers → Intake and feeds: poll a source
2. Intake and feeds → web: fetch the source
3. Intake and feeds → Built-in tools and the worker: parse in the worker
4. Intake and feeds → Catalog and search: index what was accepted
5. Intake and feeds → Inbox and digest: alert the owner

**Data leaves by rule**

1. Lifecycle and erasure → Ledgers and records: find what is due
2. Lifecycle and erasure → Grants and sharing: end its shares
3. Lifecycle and erasure → Catalog and search: remove what was derived
4. Lifecycle and erasure → Storage substrate: shred the scope key

**Two machines take turns**

1. Sync → Ledgers and records: push and pull records
2. Sync → Storage substrate: blobs and the writer epoch

**The doctor checks the install**

1. owner → Command line: run vak doctor
2. Command line → Doctor and health: collect the report
3. Admin console → Doctor and health: the Diagnostics screen
4. Doctor and health → Configuration and secrets: read the configuration
5. Doctor and health → Model providers and routing: reach the providers
6. Doctor and health → State registry and baseline: check the data

## Findings

### F1. A turn's decisions share mutable state inside two outlier functions

*Structure · Caused defects*

**Evidence.** Clippy's `cognitive_complexity` scores `Agent::run_message_inner` at 181 (rank 1 of 4,545 library functions) and `Core::run_turn_recorded` at 115 (rank 3); the median is 3 and the 99th percentile 24. 161 commits changed the first (6% of all) and 217 the second (9%). Fix commits land in `vak-core/src/lib.rs` at 10.4 and `vak-agent/src/lib.rs` at 8.9 per thousand lines, against a median of 4.0 over 420 files; file size alone does not predict the rate (ρ = -0.10).

**Why it matters.** The loop keeps the turn's decisions in mutable locals that every step and every call result updates. `948ece43d` fixed two bugs of exactly that kind: `receipts.unresolved_error` was cleared by a later success in the same batch even when an earlier call had failed, and `verification_stale` came out stale or not depending on which parallel result returned first. Both were fixed by moving the decision into a pure function over the whole batch, tested on its own. The 2026-10-22 answer investigation found another lossy decision input: plan receipts retained a deliverable name but discarded the actual form. The correction keeps active typed receipts and applies the same pure plan check in the loop and settlement, preserving exact replacement addresses. Broader state consolidation remains open.

**Fix.** Do that for the rest: the turn's state as one type, each decision a pure function of it, and the end-of-turn checks (among them goal mode's audit, the managed-work gate and the commitment hold, which judge durable work at different scopes on purpose) as one ordered list with tests of how they combine. Context planning and the model call can stay as they are.

Sources: Complexity table; `git log -L`; commit 948ece43d; `evidence.py` `hotspots`; [answer design investigation](../docs/audits/answer-design-contract-2026-10-22.md).

### F3. Storage's guarantees are not tested in the shapes that broke them

*Structure · Defects found by review*

**Evidence.** Owning the storage layer is a decision (docs/decisions.md, 2026-10-18), and it is tested for torn writes, crashes, fsync paths and injected faults, with a fuzz corpus. FinOps now compares its row projection with a direct fold, but the underlying chain reader still lacks an independent reference model, and few tests run two writer processes. The two P1 faults of 2026-10-18 needed exactly those shapes: a cached grant that kept authorizing because its revocation sat in an unreadable segment (A01), and a writer paused between the epoch check and the ref update (A02). A review's probes found them, not the suite. Repeated takeover tests now expose and cover import invalidation of encrypted projections: a standby catalog cannot outlive the imported keys. The seal-manifest verifier blind spot found on 2026-10-20 is fixed; broader interleaving and independent-reader gaps remain.

**Why it matters.** These are the guarantees authorization, erasure and sync rest on. A bug here does not show as a failed turn; it shows as access that should have ended, or a write that should have been fenced.

**Fix.** A model-based test of each chain's reader against a reference, and multi-process interleavings of every fenced write path.

Sources: [docs/audits/architecture-and-presentation-review-2026-10-18.md](../docs/audits/architecture-and-presentation-review-2026-10-18.md) (A01, A02); [conversation/evidence and import checks](../docs/audits/conversation-evidence-contract-2026-10-19.md); `crates/vak-storage`, `crates/vak-session`.

### F5. The securely confined rendered browser does not launch local Chrome

*Compatibility · Live smoke fails closed*

**Evidence.** The public example.com smoke on 2026-10-20 exits without a DOM under the new screened-proxy and native filesystem policy. Private-profile Unix IPC and private-destination rejection tests pass, but neither establishes working page rendering. The tool returns a typed error and recommends ordinary fetch; it never retries unconfined. Restricted Landlock and Docker workers also refuse until their backends enforce control-file exclusions.

**Why it matters.** Script-built pages currently lose rendered browsing on the measured Mac, and unqualified restricted backends lose worker/parser/MCP availability. Safe refusal closes the unsafe execution path but does not establish feature parity.

**Fix.** Qualify browser launch and backend control-file enforcement with real process tests, preserving proxy-only TCP, private profile state and mandatory secret/control exclusions.

Sources: [Security hardening acceptance](../docs/audits/security-hardening-2026-10-20.md); the ignored public-page browser smoke and native IPC tests.

### F6. Generated work lacks a shared kept-operation contract

*Contract · Observed in local use*

**Evidence.** The local 2026-10-22 dashboard conversation produced code, an in-process refresh timer and a file-preview card, then used nohup through Bash to claim the app was running; the next turn found no listener. Bash intentionally kills remaining process-group children on return. Managed preview lifetimes exist in the server/UI, while workspace_read inventories installed declarative workspaces rather than running artifacts. No durable duty was registered. The broader Pieces/Workers lifecycle remains unbuilt; doc 103 corrects the design, not these runtime paths. Installed follow-through on 2026-10-22 found clocks blank and planner controls absent in the default paused-code preview despite successful syntax/marker checks. A free-form edit did retain one artifact and its version history, but the open Library metadata needed refresh. A home-Space one-shot ran; registered duties in an unserved Space did not, so registration alone does not establish runner coverage.

**Why it matters.** A saved file or successful immediate HTTP check can be presented as a connected, continuing app even though no runtime owns that promise after the turn or view ends.

**Fix.** Compose existing artifact versions, one pack, broker-owned lifetimes, scoped capability bindings and Trigger-backed duties; expose the same operations to Agent/UI/CLI and check operational claims against receipts. Preserve independent passive files, installed workspaces and ordinary automations.

Sources: [Kept-work design and dated evidence](../docs/design/103-kept-work-lifecycle.md); [installed everyday-use checks](../docs/audits/kept-work-everyday-use-2026-10-22.md); [implementation gates](../docs/plans/kept-work-plan.md); `crates/vak-tools/src/bash.rs`, `crates/vak-core/src/tools_workspaces.rs`, `crates/vak-core/src/presentation_tools.rs`, `crates/vak-server/src/lib.rs`, `crates/vak-server/src/automations.rs`.

## What to keep

- **vak-permission**: 1,166 lines, declared reach, universal Allow, an adversarial escape corpus. Small and central.
- **vak-control, vak-judge, vak-lifecycle**: Pure deciders with no vak dependencies. The right shape for policy.
- **vak-context**: 2,202 lines of pure planning and assembly over the ledger.
- **vak-ooxml, vak-pdf**: No vak dependencies, bounded, fuzzable, run only in the worker.
- **The worker boundary**: A versioned protocol with 14 task kinds; parsers and tools never run in the server process.
- **Effects, runs, cursors**: At-most-once outbound actions and unknown outcomes that are never re-sent automatically.
- **The provenance gate**: Owner input and unknown editable context carry conservative provenance; private plus untrusted content requires unpreauthorizable approval for mutations and outbound tool calls in restricted modes. Remote answer media stay inert until a person follows a link.
- **The completion judges**: Whether a deliverable was produced, whether it met its requirements, a run's audited goal, a work contract and a commitment are judged separately on purpose, so produced output can never pass for proof.
- **vak-llm capability declarations**: Wire features declared by the adapter and learned from refusal, never inferred from a provider's name.
