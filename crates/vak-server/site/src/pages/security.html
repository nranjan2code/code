Nothing acts without permission

Not "the agent is careful". Every effect — a tool, a subagent, a flow, a plan, an eval, a server run, a desktop run — is evaluated by one policy engine before it happens, and there is no second path that skips it. Below is that engine's actual order of decision, and you can run it.

Run the gate

Pick a permission mode and an action. The verdict below is produced by the same precedence the engine uses: explicit deny rules, then explicit ask rules, then explicit allow rules, and only then the mode's own default.

Pick an action to see what the engine would answer.

    Deny wins outright: a matching deny rule settles the question before the mode is consulted at all, which is why a mode can never be widened into one. An ask is not a warning — the run stops, and the work it has already done is kept while it waits.

    The three modes

    A mode is a default, not a cage: your own allow, ask and deny rules compose on top of it, and deny always wins.

    read-only Reads inside the workspace are allowed; reads outside it are denied. Anything that reaches the network asks. Writes, shell commands and everything else are denied outright — not queued for approval. Use it on a repository you have not decided to trust yet.
    workspace-write The default. Reads and writes inside the canonical workspace path go through. A write outside the boundary asks; a shell command asks; anything else asks. A symlink pointing out of the workspace does not count as inside it.
    full-access No implicit boundary — which is why it cannot be reached by accident and has to be named explicitly. Your rules still sit on top of it, so this is the mode's default and not the last word.
    Changing the mode Tightening the policy cancels work already in flight and rejects approvals granted under the old policy, rather than letting them land.

    What contains a tool

    The gate decides whether an effect may happen. These decide how much a tool can reach even once it has been allowed.

    Sandboxed at the operating system Seatbelt on macOS, Landlock on Linux, and an opt-in Docker backend for Bash with no network at all.
    Restricted tools run across a broker boundary Built-in tool workers are disposable and MCP servers are sandboxed separately again, so a tool cannot reach the process that called it.
    The workspace is a real boundary Canonical path confinement with symlink-escape protection, so “inside the project” means inside the project.
    Extensions stay extensions Skills, hooks, MCP servers, custom commands and flows add capability without widening the kernel, and every one of them passes the same gate.

    Secrets, and trusting a workspace

    Opening a folder is not the same as trusting what is in it.

    Configuration resolves from broadest to narrowest — shared defaults, then per-project overrides, then per-session pins — and secrets stay out of TOML entirely. Real environment variables take precedence over any .env.

    A project's own .vak/config.toml, its .env, and its privileged settings load only after you have trusted that workspace. Until then a cloned repository cannot raise its own permission mode, register its own hooks, or point the agent at its own model endpoint by shipping a config file.

    Secrets are never forwarded as ambient Bash or MCP subprocess state, so a tool that runs does not automatically inherit your provider keys.

    Reaching it over a network

    Binding a shell-capable agent to an interface is never implicit.

    The server binds loopback by default. Binding anything else requires [server] trusted_hosts to be set, and the server refuses to start without it rather than coming up quietly on 0.0.0.0.

    Browsers sign in once, with the token the server printed, and receive an HttpOnly, SameSite=Strict cookie — the only channel that covers both fetch and server-sent events, since EventSource cannot set headers. Secure is set whenever the deployment is actually https, and deliberately not before: a browser silently discards a Secure cookie over plain http, which would make every login appear to succeed and never persist.

    On loopback there is no prompt at all. Anything that can reach loopback can already read the token off disk, so asking you to go and find one to reach the machine you are sitting at buys nothing. A request arriving with a hostname that is not in trusted_hosts is rejected before it is routed.

    The browser terminal is off by default over a network, and can be required to be loopback-only. A shell reached from a tab is a different question from a shell on your own desk, and it is answered separately.

    Failure is part of the contract

    The interesting question about a safety system is what it does on a bad day, not a good one.

    • Typed errors, bounded retries, watchdogs, circuit breakers and frozen route ladders, rather than an unbounded loop that eventually gives up.
    • Cancelling a run preserves the partial work it had already done, and says so.
    • Unattended work that needs a person suspends and queues the question instead of failing closed and losing the thread.
    • A commitment closes fulfilled only when the runtime has checked its criteria against the world; the model may propose criteria, and may never mark one passed.
    • Every commitment closes with an explicit verdict and its evidence — including an honest unknown when the runtime lost track.
